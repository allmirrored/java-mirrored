## DevOps: від коду до програми

Виконує студент у Git Bash; JDK 25 і Maven підключаються через
source doc/h07/environment.sh з кореня основного проєкту.
Лабораторія поза Git: /tmp/build-lab-h09. Неправильні Java-приклади
і згенеровані .class не додаються до основного репозиторію.

1. Створити Main.java, побачити текстовий файл, скомпілювати javac,
   побачити Main.class, виконати java Main.
2. Broken.java без крапки з комою: помилка компіляції, ненульовий код,
   Broken.class відсутній. Boom.java з виходом за межі масиву:
   компіляція успішна, виконання завершується помилкою. Скопіювати
   Boom.java до Other.java: перевірити відповідність публічного класу і файла.
3. src і out: перенести Main.java до src, старий Main.class теж до out,
   javac -d out src/Main.java. Тоді java -cp . Main має не знайти клас,
   java -cp out Main працює. У методичці старий Main.class не прибирається,
   тому просте повторення java Main могло б помилково залишитися успішним.
4. java -version і javac -version: порівняти JVM і компілятор.
5. Окремий мінімальний Maven-demo всередині лабораторії. Його власний
   pom.xml можна створювати за методичкою; основний pom.xml не змінюємо.
   Компілюємо навчальний приклад для Java 17 на встановленому JDK 25.
   mvn compile, target/classes, java -cp target/classes Main.
6. mvn test, mvn clean, повторне compile. У мінімальному demo тестів немає:
   успішний mvn test тут не доводить, що тести існують. Справжні тести h09
   перевіряються в основному проєкті. clean видаляє target, але не вихідний код.

До кожного етапу команди й момент для скриншота надаються в чаті.
Не сприймати очікувані помилки навчальних прикладів як помилки рішень h09.

## Git: гілки

Окрема неопублікована песочниця /tmp/branch-demo-h09.
Створюємо git init -b main явно: у користувача типовою могла бути master.
Ім'я і пошту автора задаємо локально, використовуючи останній коміт
основного проєкту, як у попередній самостійній.

1. Базовий коміт, refs/heads/main, HEAD: у цій песочниці loose ref
   зберігає хеш, HEAD посилається на гілку. Це навчальна модель;
   Git також може пакувати refs, тому не кожна гілка завжди окремий файл.
2. feature/notes одразу посилається на той самий коміт, файли не копіюються.
3. Новий коміт пересуває тільки поточну гілку.
4. switch змінює вміст робочих файлів відповідно до вибраної гілки.
5. switch --detach HEAD~1: HEAD містить хеш; switch - повертає назад.
6. branch -d відмовляється прибрати невлиту feature/notes; branch -D
   прибирає лише навчальне ім'я. Знайти коміт у reflog і перевірити git show.
7. experiment, перейменування на experiment/bitwise, branch -a.
   У цій песочниці немає remote, тому remotes/origin не очікуються.

feature/notes та experiment — імена з методички лише в песочниці.
Основна гілка проєкту repository-cleanup, історію й гілки проєкту не змінюємо.
Песочницю не пушимо. Рішення, тести й підтвердження h09 зберігаємо
окремим коммітом у наявному персональному репозиторії після перевірки.
