Tooling &amp; delivery track
8. Оточення
Змінні з заняття 5 жили всередині одного shell. Змінні оточення — це ті самі змінні, але
передані процесам, які ви запускаєте. Різниця в одному слові export: без нього змінна лишається
локальною, з ним — потрапляє в кожен дочірній процес. Так програму налаштовують ззовні, не
змінюючи ані її код, ані файли на диску.
Найважливіша з них — PATH: список тек, розділених двокрапками, у яких shell шукає програму
за іменем. Це вичерпне пояснення «command not found»: файл може бути на диску, а теки з ним
немає в списку. І пояснення того, чому свою програму запускають як ./script.sh — поточної
теки в PATH немає, і це зроблено навмисно, з міркувань безпеки.
HOME — ваша домашня тека; ~ розкривається саме в неї. Далі йдуть змінні, які читають конкретні
програми: JAVA_HOME для збірок, EDITOR для редактора за замовчуванням, і безліч інших.
Налаштування, які мають пережити перезапуск термінала, кладуть у файл запуску shell: для zsh
це ~/.zshrc, для bash — ~/.bashrc. Він виконується при кожному відкритті нового термінала.
Туди ж кладуть aliases — короткі імена для довгих команд. Oh My Zsh — популярний набір
готових налаштувань: запрошення, що показує поточну гілку Git, автодоповнення й плагіни.
Завдання
1. Побачте різницю між змінною shell і змінною оточення.
MY_LOCAL=локальна
export MY_EXPORTED=експортована
echo &quot;$MY_LOCAL / $MY_EXPORTED&quot;
bash -c &#39;echo &quot;у дочірньому: [$MY_LOCAL] [$MY_EXPORTED]&quot;&#39;
У дочірньому процесі перша порожня, друга — ні. Це і є все значення слова export.
2. Прочитайте PATH як список.
echo $PATH
echo $PATH | tr &#39;:&#39; &#39;\n&#39;
which java
which git
tr замінив двокрапки на переноси — і список став читабельним. Далі знайдіть, з якої саме теки
береться кожна програма.
3. Відтворіть «command not found» і полагодьте.
mkdir -p ~/bin
cat &gt; ~/bin/hello &lt;&lt;&#39;EOF&#39;
#!/bin/bash
echo &quot;Привіт із власної програми&quot;
EOF
chmod +x ~/bin/hello
hello
Помилка: файл є, теки в PATH немає. Тепер:
export PATH=&quot;$PATH:$HOME/bin&quot;
hello
which hello

Працює. Відкрийте новий термінал і виконайте hello ще раз — знову помилка, бо export діяв
лише в тому shell.
4. Зробіть налаштування постійним.
echo &#39;export PATH=&quot;$PATH:$HOME/bin&quot;&#39; &gt;&gt; ~/.zshrc
tail -3 ~/.zshrc
source ~/.zshrc
hello
source виконує файл у поточному shell, не породжуючи дочірнього, — тому зміни діють одразу.
Відкрийте новий термінал і переконайтеся, що тепер працює й там.
5. Заведіть aliases.
alias gs=&quot;git status -s&quot;
alias gl=&quot;git log --oneline --graph --decorate -20&quot;
gs
gl
alias
Останній рядок покаже всі наявні. Якщо стало зручно — додайте ці два рядки в ~/.zshrc поруч
із PATH.
6. Налаштуйте програму через оточення.
export EDITOR=nano
git config --global core.editor &quot;$EDITOR&quot;
printenv EDITOR
printenv HOME
env | sort | head -20
printenv друкує одну змінну, env — усі. Порівняйте кількість рядків у env із тим, що ви
оголошували самі: більшість поставила система.
7. Подивіться, що змінює Oh My Zsh. Якщо він у вас є — зайдіть у теку з Git-репозиторієм і
подивіться на запрошення: воно показує поточну гілку. Якщо немає, встановіть за інструкцією з
офіційного сайту й порівняйте вигляд термінала до й після. Потім:
type gs
type ls
type розрізняє alias і програму (заняття 3) — тепер ви бачите, звідки береться кожна назва, яку
набираєте.
Що з цього винести
export перетворює змінну shell на змінну оточення, видиму дочірнім процесам. PATH — список
тек пошуку й повна відповідь на «command not found». ~/.zshrc виконується при кожному
відкритті термінала, тому постійні налаштування живуть там, а source застосовує їх без
перезапуску. Aliases економлять набір, type показує, що насправді ховається за іменем.

Git track
8. Скасування змін
Найчастіше питання до Git — «як відкотити». Відповідей кілька, бо відкотити можна різні речі:
правку у файлі, факт стейджингу, останній коміт, коміт, який уже бачили інші. Плутають їх
тому, що слово одне, а стани різні.
git commit --amend замінює останній коміт новим. Слово «замінює» тут точне: старий коміт не
редагується, створюється інший, з іншим хешем, а гілка переставляється на нього. Це важливо,
бо все, що змінює вже наявні коміти, змінює їхні хеші — а отже, стає небезпечним, щойно коміт
побачив хтось інший.
git restore &lt;file&gt; викидає незакомічені правки у файлі — з диска, без відновлення. git
restore --staged &lt;file&gt; прибирає файл зі staging area, лишаючи правки. Дві дуже схожі
команди, і різницю варто побачити на практиці, а не запам&#39;ятати з тексту.
git reset переставляє гілку назад, а прапорець вирішує долю вашої роботи. --soft лишає зміни
застейдженими, --mixed (типовий) — у working tree, --hard знищує їх. Саме --hard заслужив
Git репутацію страшного інструмента.
І тут з&#39;являється git reflog — журнал усіх позицій, де побував HEAD. Він локальний, його ніхто
не бачить, і він зберігає навіть ті коміти, на які більше ніщо не вказує. Це і є підстава для
твердження «Git майже ніколи не втрачає закомічене».
Нарешті, git revert — протилежність усьому попередньому: він не переписує історію, а
дописує новий коміт, що скасовує старий. Правило просте: якщо коміт уже на сервері й хтось
міг його забрати — тільки revert.
Завдання
1. Виправте останній коміт.
mkdir -p /tmp/undo-demo &amp;&amp; cd /tmp/undo-demo &amp;&amp; git init
echo &quot;перший&quot; &gt; a.txt &amp;&amp; git add a.txt &amp;&amp; git commit -m &quot;опечатка в повідмоленні&quot;
git log --oneline
git commit --amend -m &quot;правильне повідомлення&quot;
git log --oneline
Порівняйте хеші до й після. Вони різні — це не той самий коміт із виправленим текстом, це
новий коміт. Запам&#39;ятайте цей факт: він пояснює половину проблем із push після amend.
2. Додайте забутий файл до останнього коміту.
echo &quot;забув&quot; &gt; b.txt
git add b.txt
git commit --amend --no-edit
git show --stat HEAD
--no-edit означає «лиши повідомлення як є». У коміті тепер два файли.
3. Побачте різницю між двома restore.
echo &quot;правка&quot; &gt;&gt; a.txt
git add a.txt
echo &quot;ще правка&quot; &gt;&gt; a.txt
git status -s
Дві колонки показують: одна зміна застейджена, одна ні. Тепер:

git restore --staged a.txt
git status -s
cat a.txt
Зміни на місці, зі staging area прибрані. А тепер справді небезпечна команда:
git restore a.txt
cat a.txt
Правки зникли назавжди — вони ніколи не були в жодному коміті, тож відновлювати нема
звідки. Це єдина команда в занятті, яка справді втрачає роботу.
4. Порівняйте три reset з однієї точки. Зробіть три коміти й перевірте кожен прапорець:
for i in 1 2 3; do echo &quot;рядок $i&quot; &gt;&gt; log.txt; git add log.txt; git commit -m
&quot;коміт $i&quot;; done
git log --oneline
git reset --soft HEAD~1 &amp;&amp; git status -s &amp;&amp; git log --oneline
git commit -m &quot;коміт 3&quot; # повернули як було
git reset --mixed HEAD~1 &amp;&amp; git status -s &amp;&amp; git log --oneline
git add log.txt &amp;&amp; git commit -m &quot;коміт 3&quot;
git reset --hard HEAD~1 &amp;&amp; git status -s &amp;&amp; git log --oneline
Після --soft зміна застейджена, після --mixed — у working tree, після --hard її немає ніде. Три
команди, один рух гілки, три різні долі вашої роботи.
5. Поверніть те, що знищив --hard.
git reflog
Знайдіть рядок із «коміт 3» і візьміть його хеш:
git reset --hard &lt;hash-із-reflog&gt;
git log --oneline
Коміт повернувся. Ось чому --hard страшний, але не фатальний: доки коміт існував, він
лишається в базі об&#39;єктів, і reflog знає дорогу до нього.
6. Скасуйте коміт, не переписуючи історію.
git revert HEAD --no-edit
git log --oneline
cat log.txt
Історія стала довшою, а не коротшою: старий коміт на місці, поруч новий, що його скасовує.
Саме так скасовують те, що вже відправлено на сервер.
Що з цього винести
restore працює з файлами, reset — з гілкою, revert — з історією. Усе, що змінює наявні
коміти (amend, reset), створює нові хеші й тому безпечне лише до push. Після push — тільки
revert. І перш ніж панікувати через втрачений коміт, виконайте reflog.
