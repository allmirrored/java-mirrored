Tooling &amp; delivery track
7. Порти й localhost
Досі програми обмінювалися даними через файли. Мережа додає інший спосіб: програма слухає
порт — тобто каже операційній системі «з&#39;єднання, що приходять на номер 8080, передавай
мені». Порт — просто число від 1 до 65535, і воно нічого не означає саме собою; домовленості
на кшталт 80 для HTTP і 443 для HTTPS — саме домовленості.
localhost — ім&#39;я вашого власного комп&#39;ютера в мережевих термінах, йому відповідає адреса
127.0.0.1. Звернення на localhost:8080 не виходить назовні: воно доходить до програми, що
працює тут-таки. Саме тому розробка виглядає як «запустив сервер — відкрив браузер»: два
процеси на одній машині спілкуються мережевим способом.
Із цього випливає найчастіша помилка початківця — «address already in use». Порт може
слухати лише один процес. Повідомлення означає рівно те, що написано: хтось уже там. Не
конфлікт версій, не поламаний проєкт — просто попередній запуск не завершився.
Перевіряти з&#39;єднання зручно curl — це браузер без вікна: він надсилає HTTP-запит і друкує
відповідь у термінал. Прапорець -i додає заголовки, і саме в них видно код відповіді (200, 404,
500), який часто і є всією потрібною інформацією.
Завдання
1. Запустіть слухача й переконайтеся, що він слухає.
cd ~/dev/files-lab
python3 -m http.server 8000 &amp;
lsof -i :8000
Вивід lsof показує процес, PID і порт. Це головна команда заняття: вона відповідає на питання
«хто зайняв порт».
2. Зверніться до нього трьома способами.
curl http://localhost:8000
curl http://127.0.0.1:8000
curl -i http://localhost:8000
Перші два дають однакове — це одна й та сама машина під двома іменами. Третій показує
заголовки; знайдіть у першому рядку код 200.
3. Отримайте помилку навмисно.
curl -i http://localhost:8000/no-such-file
curl -i http://localhost:9999
Перша дає 404 — сервер відповів, файлу немає. Друга не дає коду взагалі: там ніхто не слухає, і
curl скаржиться на з&#39;єднання. Різницю між «сервер відповів помилкою» і «сервера немає» треба
чути з першого разу.
4. Відтворіть «address already in use».
python3 -m http.server 8000
Друга спроба зайняти той самий порт провалюється. Прочитайте повідомлення. Тепер знайдіть
винуватця й приберіть його:
lsof -i :8000
kill &lt;PID&gt;

python3 -m http.server 8000 &amp;
lsof -i :8000
Це повний цикл діагностики, яким ви користуватиметеся всю кар&#39;єру.
5. Подивіться на всі слухаючі порти системи.
lsof -nP -iTCP -sTCP:LISTEN
netstat -an | grep LISTEN
Дві команди, схожий результат. netstat є майже скрізь, lsof детальніший, бо називає процес.
На Linux те саме зазвичай роблять командою ss -tlnp.
6. Перевірте порт без HTTP.
nc -z localhost 8000; echo &quot;exit code: $?&quot;
nc -z localhost 9999; echo &quot;exit code: $?&quot;
nc -z лише перевіряє, чи приймають з&#39;єднання, і відповідає exit-кодом із заняття 3. Це зручно у
скриптах: «дочекайся, поки сервер підніметься».
7. Приберіть за собою.
jobs
kill %1
lsof -i :8000
Порожній вивід lsof — доказ, що порт вільний.
Що з цього винести
Слухати порт означає «приймати з&#39;єднання за номером»; порт слухає рівно один процес.
localhost — ваша ж машина. lsof -i :ПОРТ відповідає, хто його зайняв, і разом із kill
розв&#39;язує «address already in use» за два кроки. curl -i показує код відповіді, і відсутність коду
— це зовсім інша помилка, ніж 404.

Git track
7. Порівняння версій
git diff — команда, яка найчастіше «не працює» в новачків, і причина завжди та сама: вона
порівнює не те, що ви думаєте. Diff завжди має дві сторони, і різні форми команди беруть різні
пари з трьох станів, які ви вже знаєте з заняття 3: working tree, index, останній коміт.
git diff без аргументів порівнює working tree з index — тобто показує незастейджені зміни.
Щойно ви зробили add, ця команда замовкає, і саме тут студенти вирішують, що diff зламався.
git diff --staged порівнює index з останнім комітом — показує те, що потрапить у наступний
коміт. git diff HEAD порівнює working tree з комітом, тобто все разом, застейджене й ні.
Читати diff теж треба навчитися. Рядок @@ -12,7 +12,9 @@ — це заголовок фрагмента (hunk): у
старій версії з 12-го рядка йшло 7 рядків, у новій з 12-го йде 9. Далі рядки з - — те, що було, з +
— те, що стало, без знаку — незмінний контекст навколо. Git не зберігає діфів (заняття 2), він
обчислює їх щоразу — тому їх можна питати між будь-якою парою станів.
Звичка, заради якої все це: читати власний diff перед комітом. Більшість випадкових комітів
— залишений System.out.println, закоментований блок, зайвий файл — коштують десять
секунд перегляду.
Завдання
1. Відтворіть «diff зламався».
mkdir -p /tmp/diff-demo &amp;&amp; cd /tmp/diff-demo &amp;&amp; git init
printf &#39;один\nдва\nтри\n&#39; &gt; f.txt
git add f.txt &amp;&amp; git commit -m &quot;початок&quot;
printf &#39;чотири\n&#39; &gt;&gt; f.txt
git diff
Зміна видно. Тепер:
git add f.txt
git diff
Порожньо. Команда не зламалася — вона порівнює working tree з index, а вони тепер однакові.
2. Спитайте про решту двох пар.
git diff --staged
git diff HEAD
Перша показує зміну (index проти коміту), друга теж (working tree проти коміту). Додайте ще
одну незастейджену правку й повторіть усі три команди — тепер вони дадуть три різні
відповіді. Випишіть на аркуші, яка з чим порівнює; це найкорисніші тридцять секунд усього
заняття.
3. Прочитайте заголовок фрагмента.
printf &#39;нуль\n&#39; &gt; f.txt
printf &#39;один\nдва\nтри\n&#39; &gt;&gt; f.txt
git diff
Знайдіть рядок із @@ і розберіть чотири числа. Потім змініть кількість контексту:
git diff -U0
git diff -U5

Той самий diff, різна кількість незмінних рядків навколо. Це не косметика: коли шукаєте
причину зміни, ширший контекст часто одразу показує, у якій функції вона сталася.
4. Порівняйте два коміти.
git add . &amp;&amp; git commit -m &quot;друга версія&quot;
git log --oneline
git diff HEAD~1 HEAD
git diff HEAD~1
Останні дві команди дають те саме: якщо другу сторону не назвати, Git бере working tree.
5. Звузьте diff до одного шляху.
echo &quot;інший файл&quot; &gt; other.txt
git add other.txt
git diff --staged
git diff --staged -- f.txt
Подвійна риска -- відокремлює шляхи від решти аргументів. Вона потрібна щоразу, коли ім&#39;я
файлу збігається з іменем гілки, — і це рятує від дуже заплутаних помилок.
6. Подивіться на масштаб, а не на вміст.
git diff --stat HEAD~1
git diff --shortstat HEAD~1
--stat дає перелік файлів із кількістю змінених рядків. На великій зміні це перше, що варто
подивитися: воно відповідає на питання «наскільки це велике й чого воно торкається» до того, як
ви почнете читати рядки.
7. Порівняйте текст по словах. Для конспектів і документації це важливіше, ніж для коду:
printf &#39;Алгоритм має бути скінченним.\n&#39; &gt; text.md
git add text.md &amp;&amp; git commit -m &quot;текст&quot;
printf &#39;Алгоритм має бути скінченним і детермінованим.\n&#39; &gt; text.md
git diff
git diff --word-diff
Звичайний diff показує рядок видаленим і доданим цілком; --word-diff показує, що змінилося
одне слово. У репозиторії з лекціями це різниця між «нічого не зрозуміло» і «бачу правку».
8. Виробіть звичку. Перед кожним комітом у домашньому завданні виконуйте:
git diff --staged
і лише потім git commit. Якщо помітили щось зайве — приберіть зі staging area командою git
restore --staged &lt;file&gt; із заняття 3.
Що з цього винести
Три стани дають три пари, і кожна форма diff бере свою: без аргументів — working tree проти
index, --staged — index проти коміту, HEAD — working tree проти коміту. Порожній вивід майже
завжди означає, що ви спитали не ту пару. А --stat перед читанням рядків і --staged перед
комітом — дві звички, які варто закріпити зараз.
